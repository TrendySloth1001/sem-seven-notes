**In simple words:** a traditional database keeps structured data in tables on one strong server. Big data is so large, so fast and so mixed that it needs many machines working together. <Cite id="big-data-intro-oracle" /> <Cite id="big-data-intro-av" />

| Point | Traditional database | Big data |
|---|---|---|
| Size | Megabytes to a few terabytes. | Terabytes to petabytes and more. |
| Data type | Mostly structured (tables). | Structured, semi-structured and unstructured. |
| Schema | Fixed before storing (schema-on-write). | Flexible, applied when reading (schema-on-read). |
| Growth | Slow and predictable. | Fast and continuous. |
| Scaling | Scale up: buy a bigger, costlier server. | Scale out: add many cheap nodes. |
| Processing | One machine; data is brought to the program. | Cluster; the program is sent to the data. |
| Arrival | Mostly batch updates. | Batch and real-time streams. |
| Tools | RDBMS, SQL, data warehouse. | Hadoop, Spark, NoSQL, Kafka. |
| Failure | Server failure is serious. | Node failure is expected and handled by copies. |
| Cost | Costly hardware and licences. | Cheap hardware, often open source. |

<Cite id="big-data-intro-mmds" /> <Cite id="big-data-intro-gfg" />

**Example.** A college fee record fits a traditional database. Clicks, videos and sensor readings of millions of users need big data tools.

**Conclusion:** a traditional database is best for small, structured, transactional data; big data systems are needed when volume, velocity and variety are beyond one machine.
