**In simple words:** CAP theorem kehta hai ki distributed data store network toot jaane par Consistency, Availability aur Partition tolerance teeno ek saath poori tarah nahi de sakta. ACID alag list hai: ek single database transaction ke promises. <Cite id="nosql-intro-wiki-cap" /> <Cite id="nosql-intro-gfg-cap" />

**CAP theorem (Eric Brewer).**

- **Consistency (C):** har read ko latest write dikhta hai.
- **Availability (A):** working node ko bheji har request ka reply milta hai.
- **Partition tolerance (P):** network split ho jaaye tab bhi system chalta rehta hai.

Cluster mein partitions hote hi hain, isliye partition aane par choose karna padta hai: correct rehna par kuch requests refuse karna (**CP**, jaise HBase), ya hamesha reply dena par shayad purane data ke saath (**AP**, jaise Cassandra). Partition na ho to dono mil sakte hain. Brewer khud "koi do chuno" ko misleading simplification kehte hain. <Cite id="nosql-intro-brewer-cap12" />

**ACID:** Atomicity (saare steps ya koi nahi), Consistency (data valid rehta hai), Isolation (parallel transactions ek dusre ko disturb nahi karte), Durability (save hua data crash ke baad bhi bachta hai). <Cite id="nosql-intro-wiki-acid" />

| Point | ACID | CAP |
|---|---|---|
| About | Database ke andar transactions | Network failure mein distributed system |
| Properties | Atomicity, Consistency, Isolation, Durability | Consistency, Availability, Partition tolerance |
| "Consistency" ka matlab | Data rules follow karta hai | Saare nodes latest value dikhate hain |
| Goal | Correct transactions | Correctness aur uptime ka trade-off |
| Typical systems | RDBMS | Distributed NoSQL stores |

Bahut se NoSQL stores ACID ki jagah BASE (Basically Available, Soft state, Eventually consistent) chunte hain. <Cite id="nosql-intro-wiki-ec" />

**Conclusion:** ACID ek transaction ko protect karta hai; CAP batata hai ki data ko network pe failane ki kya keemat hai.
