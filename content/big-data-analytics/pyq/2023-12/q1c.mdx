**In simple words:** the CAP theorem says a distributed data store cannot fully give Consistency, Availability and Partition tolerance all together when the network breaks. ACID is a different list: the promises of a single database transaction. <Cite id="nosql-intro-wiki-cap" /> <Cite id="nosql-intro-gfg-cap" />

**CAP theorem (Eric Brewer).**

- **Consistency (C):** every read sees the latest write.
- **Availability (A):** every request to a working node gets a reply.
- **Partition tolerance (P):** the system keeps working when the network splits.

Partitions do happen in a cluster, so when one occurs we must choose: stay correct but refuse some requests (**CP**, for example HBase), or always reply but maybe with old data (**AP**, for example Cassandra). Without a partition we can have both. Brewer himself calls "pick any two" a misleading simplification. <Cite id="nosql-intro-brewer-cap12" />

**ACID:** Atomicity (all steps or none), Consistency (data stays valid), Isolation (parallel transactions do not disturb each other), Durability (saved data survives a crash). <Cite id="nosql-intro-wiki-acid" />

| Point | ACID | CAP |
|---|---|---|
| About | Transactions inside a database | A distributed system during a network failure |
| Properties | Atomicity, Consistency, Isolation, Durability | Consistency, Availability, Partition tolerance |
| "Consistency" means | Data obeys the rules | All nodes show the latest value |
| Goal | Correct transactions | Trade-off between correctness and uptime |
| Typical systems | RDBMS | Distributed NoSQL stores |

Many NoSQL stores choose BASE (Basically Available, Soft state, Eventually consistent) instead of ACID. <Cite id="nosql-intro-wiki-ec" />

**Conclusion:** ACID protects one transaction; CAP describes the price of spreading data over a network.
