**In simple words:** Hadoop is excellent for storing and batch-processing huge files on cheap machines, but it is the wrong tool for some jobs. <Cite id="mapreduce-gfg-proscons" />

1. **Small files problem.** The NameNode keeps the metadata of every file and block in memory, so millions of tiny files exhaust its memory. HDFS is designed for a few very large files. <Cite id="hdfs-apache-design" />
2. **Batch only, high latency.** A MapReduce job takes seconds to minutes to start, so it cannot give real-time answers or handle live streams.
3. **Slow for iterative work.** Machine learning and graph algorithms repeat many passes. MapReduce writes results to disk after every job, which makes each pass slow (Spark keeps data in memory instead).
4. **Write-once files.** HDFS allows append but not random in-place updates, so it does not suit frequently changing data. <Cite id="hdfs-apache-design" />
5. **Complex programming.** Writing a simple join or a multi-step pipeline in raw Java MapReduce takes a lot of code; Hive and Pig were added to hide this.
6. **Security is weak by default.** Kerberos has to be configured, and data is not encrypted unless set up.
7. **Storage overhead.** Three-way replication means 1 TB of data takes 3 TB of disk.
8. **Single master.** The NameNode is a bottleneck and was a single point of failure; High Availability setups are needed to remove this.

**Conclusion:** Hadoop suits large, batch, write-once data. For real-time, iterative or small-file workloads, tools such as Spark, HBase or streaming systems are used. <Cite id="hadoop-ecosystem-gfg-hadoop-ecosystem" />
