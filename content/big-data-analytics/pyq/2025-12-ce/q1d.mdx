**In simple words:** **recall** asks: "of all the items that really are in the set, how many did the filter find?" A Bloom filter never says "no" for an item that was inserted, so it finds every one of them. That is why its recall is 100%. <Cite id="stream-counting-mmds-home" loc="§4.3" /> <Cite id="stream-counting-wiki-bloom" />

$$
\text{recall} = \frac{TP}{TP + FN}
$$

$TP$ (true positives) are inserted items the filter says "present". $FN$ (false negatives) are inserted items the filter says "absent".

**Why $FN = 0$**

1. Inserting an item sets its $k$ bits to 1.
2. A bit is never turned back to 0. There is no delete.
3. At look-up time the same $k$ bits are computed again and are still all 1, so the answer is always "possibly present".
4. So no inserted item is ever rejected: $FN = 0$ and recall $= TP/(TP + 0) = 1 = 100\%$.

<Img id="img-bda-n2-bloom" caption="Each inserted item (x, y, z) sets its own bits to 1, and those bits stay 1. A look-up of any inserted item therefore finds all its bits set." />

| Item looked up | Truth | Filter says | Result |
|---|---|---|---|
| Was inserted | present | possibly present | True positive (always) |
| Was never inserted, one bit is 0 | absent | definitely absent | True negative |
| Was never inserted, all bits are 1 by other items | absent | possibly present | **False positive** |
| Was inserted | present | definitely absent | **Impossible** |

**The price.** The errors are all on the other side. Different items can share bits, so some absent items look present (false positives), and **precision** is below 100%. The false-positive rate grows as the array fills up. Bloom filters are used where a wrong "yes" is cheap (check the slow exact store next) but a wrong "no" would be harmful. <Cite id="stream-counting-gfg-bloom" />

**Conclusion:** bits are only ever set, never cleared, so an inserted item always passes. Recall is 100%, and only precision suffers.
