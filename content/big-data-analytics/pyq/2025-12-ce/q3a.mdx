**In simple words:** a **Bloom filter** is a tiny bit array that answers "have I seen this item before?" using very little memory. It may say "yes" wrongly (a **false positive**) but it **never says "no" wrongly** (no false negative). <Cite id="stream-counting-mmds-home" loc="§4.3" /> <Cite id="stream-counting-wiki-bloom" />

**Why it is needed.** A mail server holding a billion good addresses cannot afford a disk look-up for every mail. A Bloom filter keeps a few bits per address in memory. "No" is certain and needs no further check; "probably yes" is checked against the slow exact list. <Cite id="stream-counting-gfg-bloom" />

**Parts and working**

1. A bit array of $m$ bits, all 0 at the start, and $k$ hash functions, each giving a position from 0 to $m - 1$.
2. **Insert** $x$: compute the $k$ positions and set those bits to 1.
3. **Look up** $y$: compute the same positions. If **any** bit is 0, $y$ is definitely absent. If **all** are 1, $y$ is probably present.

<Img id="img-bda-n2-bloom" caption="Each item sets k bits to 1. A look-up checks the same bits, and one 0 bit is enough to say the item is surely absent." />

**Properties.** Bits are never cleared, so there are no false negatives. Other items can set the same bits, so false positives happen, and their rate grows as the array fills. Items cannot be deleted or listed. <Cite id="stream-counting-mmds-home" loc="§4.3" />

<Sum>

<Given>

$m = 5$ bits (positions 0 to 4), all 0. $h_1(x) = x \bmod 5$ and $h_2(x) = (2x + 6) \bmod 5$. Insert 10 and 7.

</Given>

<Find>

the bit array after both insertions (and test two more values).

</Find>

<Steps>

1. **Insert 10.** $h_1 = 10 \bmod 5 = 0$. $h_2 = (20 + 6) \bmod 5 = 26 \bmod 5 = 1$. Set bits 0 and 1: `11000`.
2. **Insert 7.** $h_1 = 7 \bmod 5 = 2$. $h_2 = (14 + 6) \bmod 5 = 20 \bmod 5 = 0$. Set bits 2 and 0 (bit 0 is already 1): `11100`.
3. Final array:

   | position | 0 | 1 | 2 | 3 | 4 |
   |---|---|---|---|---|---|
   | bit | 1 | 1 | 1 | 0 | 0 |

4. **Test 3.** $h_1 = 3$, and bit 3 is 0, so 3 is **definitely absent**.
5. **Test 12.** $h_1 = 12 \bmod 5 = 2$ and $h_2 = (24 + 6) \bmod 5 = 0$. Bits 2 and 0 are both 1, so the filter says "probably present", but 12 was never inserted: a **false positive**.

</Steps>

<Answer>

bits 0, 1 and 2 are set: the array is `11100`. (Test: 3 is absent, 12 is a false positive.)

</Answer>

<Box kind="verify">

Union of the positions: \{0, 1\} and \{2, 0\} give \{0, 1, 2\}, so 3 bits are 1. Re-check each hash: $26 = 5 \times 5 + 1$, $20 = 5 \times 4 + 0$. Both inserted items still pass their own test (10 uses bits 0 and 1, 7 uses bits 2 and 0), as a filter with no false negatives must. The array is small (3 of 5 bits set), so a random new item passes with chance about $(3/5)^2 = 0.36$, and a false positive like 12 is not surprising.

</Box>

</Sum>

**Advantages.** Very small memory, constant-time insert and look-up, no false negatives, works on streams. **Disadvantages.** False positives, no deletion (a counting Bloom filter fixes this with counters), cannot list the items. <Cite id="stream-counting-gfg-counting-bloom" />

**Applications.** Spam and blacklist checks. Cassandra and HBase keep a Bloom filter per data file to skip files that surely lack a key. Redis offers a ready Bloom filter. <Cite id="stream-counting-cass-bloom" /> <Cite id="stream-counting-redis-bloom" />

**Conclusion:** a Bloom filter trades a small chance of a false "yes" for a big saving in memory. Here, inserting 10 and 7 gives `11100`.
