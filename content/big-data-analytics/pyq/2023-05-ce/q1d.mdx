**In simple words:** a data stream is an endless flow of items (sensor readings, clicks, tweets). Queries on it are **continuous**: they are registered once and keep giving answers as new data arrives. This is much harder than querying a stored table. <Cite id="stream-data-model-babcock2002" /> <Cite id="stream-data-model-geisler" />

**Issues and challenges:**

1. **Unbounded data, limited memory.** The stream never ends, so it cannot all be stored. Only a small summary can be kept.
2. **One pass, fast arrival.** Each item is seen once and the system cannot control the rate. Processing must keep up with the speed, or items are lost.
3. **Approximate answers.** Many exact answers (such as distinct count) need unbounded memory. So we accept approximate answers from samples, sketches and histograms, with known error.
4. **Blocking operators.** Sort, aggregate and join normally need all the input. On a stream they never finish, so they must work on a **sliding window** of the latest items. <Cite id="stream-data-model-gfg-dbms-dsms" />
5. **Window and time handling.** Choosing window size and handling late or out-of-order items is difficult.
6. **Many standing queries.** Hundreds of continuous queries share limited CPU and memory. The system must share work and, when overloaded, **shed load** (drop some data) in a controlled way.
7. **Ad-hoc queries on the past.** Old data is gone, so queries about it can only be answered from the stored summaries.

**Conclusion:** stream query processing must work with bounded memory, one pass, windows and approximate answers, unlike an ordinary DBMS.
