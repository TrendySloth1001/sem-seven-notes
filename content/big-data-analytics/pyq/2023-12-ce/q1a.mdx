**In simple words:** an **RDBMS** (MySQL, Oracle) keeps neat tables on one strong server and answers SQL queries fast. **Hadoop** is a framework that stores any kind of data across many cheap machines and processes it in parallel. The basic difference: an RDBMS is built for small or medium **structured** data with transactions, while Hadoop is built for **huge, varied** data processed in batches. <Cite id="hadoop-ecosystem-gfg-hadoop-intro" /> <Cite id="hadoop-ecosystem-tp-hadoop-overview" />

| Point | Traditional RDBMS | Hadoop |
|---|---|---|
| Data type | Structured (tables, fixed schema) | Structured, semi-structured and unstructured |
| Data size | Gigabytes to a few terabytes | Terabytes to petabytes |
| Schema | Schema on write: design the table, then load | Schema on read: load the file, give it structure when reading |
| Scaling | Scale up (a bigger server), costly | Scale out (add cheap nodes) |
| Hardware | Expensive high-end servers | Commodity hardware |
| Processing | SQL, quick on indexed data | Batch jobs (MapReduce, Spark), huge throughput |
| Updates | Read and write many times | Write once, read many times |
| Transactions (ACID) | Fully supported | Not designed for them |
| Fault tolerance | Needs extra set-up | Built in (replication, task re-run) |

**Example:** a bank keeps account balances in an RDBMS because every transfer must be exact and instant. The same bank analyses years of web logs and call recordings in Hadoop. <Cite id="big-data-intro-wiki-rdbms" /> <Cite id="hadoop-ecosystem-wiki-hadoop" />

**Conclusion:** use an RDBMS for fast transactions on structured data and Hadoop for analysing very large, mixed data; they often work together.
