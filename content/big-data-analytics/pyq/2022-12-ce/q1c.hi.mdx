**In simple words:** HDFS kuch bahut bade files store karne aur unhe shuru se end tak tezi se padhne ke liye bana hai. Lakhon chhote files ke liye ye acchha nahi, kyunki har file NameNode ki memory leti hai aur har read mein seek lagta hai. <Cite id="hdfs-apache-design" /> <Cite id="hdfs-gfg" />

**Bade datasets HDFS ko kyun suit karte hain**

1. **Bade blocks:** files bade blocks mein kat-ti hain (default 128 MB) aur kai DataNodes pe phailti hain, to ek file kisi ek disk se bhi badi ho sakti hai.
2. **Streaming reads:** bade block mein ek seek ke baad lamba sequential read hota hai, jisse high throughput milta hai. <Cite id="hdfs-apache-design" />
3. **Replication:** har block ki copies hoti hain (default 3), to machine fail ho to kuch nahi khota.
4. **Computation data ke paas jaata hai:** MapReduce task usi node pe chalta hai jahan block hai.

**Chhote files kyun nuksaan karte hain**

1. NameNode har file, directory aur block ka metadata RAM mein rakhta hai, lagbhag 150 bytes har ek ka. Ek crore one-block files ko lagbhag 3 GB NameNode memory chahiye, aur ek arab files infeasible hain. <Cite id="hdfs-cloudera-small" />
2. 1 MB ki file bhi ek block entry leti hai, to memory data pe nahi metadata pe waste hoti hai.
3. Bahut saare chhote files padhne mein bahut seeks aur DataNodes ke beech hops lagte hain, aur MapReduce har chhote file ke liye ek map task start karta hai, to task start-up time hi zyada ho jaata hai.

**Fix:** chhote files ko SequenceFile, HAR file jaise container mein pack karo. <Cite id="hdfs-cloudera-small" />

**Conclusion:** HDFS bahut saare chhote files ka low-latency access chhod kar kuch bade files pe high throughput leta hai.

Exam mein English mein likho: "HDFS is designed for large files with streaming access; small files overload the NameNode memory."
