**In simple words:** Google ko web jitna bada data process karna tha (crawling, indexing, ranking). Ek bada expensive server ye time pe nahi kar sakta tha, isliye Google ne **MapReduce** banaya: kaam ko chhote map aur reduce tasks mein todo aur hazaaron sasti machines pe chalao. Ye NoSQL-era ki standard case study hai ki business problem faster, cheaper aur more effectively kaise solve hui. <Cite id="big-data-intro-mapreduce" /> <Cite id="big-data-intro-nosql" />

**Business drivers** (McCreary aur Kelly ke chaar drivers):

| Driver | Google MapReduce case mein |
|---|---|
| Volume | Arabon web pages, ek server store ya scan nahi kar sakta. |
| Velocity | Web badalta rehta hai, to index aur statistics baar-baar chahiye. |
| Variability | Pages, logs aur links ki koi fixed shape nahi, to fixed table fit nahi hota. |
| Agility | Engineers ko naye analysis jaldi likhne hain, parallel programming seekhe bina. |

**Ye problem kaise solve hui**

1. Data ko bahut saari commodity machines pe rakho (GFS mein) aur **code ko data ke paas bhejo**, data ko code ke paas nahi.
2. Programmer sirf `map` aur `reduce` likhta hai; splitting, scheduling, shuffling aur machine failures library sambhalti hai. <Cite id="hadoop-ecosystem-dean2004" />
3. Zyada speed chahiye to aur sasti machines jodo (scale out).

**Findings**

- **Faster:** hazaaron machines ek hi job pe ek saath kaam karti hain.
- **Cheaper:** ek mehnga bada server ki jagah ordinary hardware, aur fail hui machine ka task kahin aur dobara chal jaata hai.
- **More effective:** parallel computing na jaanne wale programmers bhi jobs likh sakte the; paper ke mutabik Google mein September 2004 tak lagbhag 900 MapReduce programs the aur August 2004 mein 29,423 jobs chale. <Cite id="big-data-intro-mapreduce" />

**Conclusion:** MapReduce dikhata hai ki data bahut bada ho jaye to scale-out, shared-nothing processing time, cost aur ease of use mein single bade server se behtar hai. <Cite id="nosql-intro-gfg-intro" />

Exam mein English mein likho: "MapReduce solved Google's volume problem faster and cheaper using commodity clusters."
