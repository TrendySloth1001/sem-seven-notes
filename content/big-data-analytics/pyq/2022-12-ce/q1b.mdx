**In simple words:** Google had to process web-sized data (crawling, indexing, ranking). One big expensive server could not do it in time, so Google built **MapReduce**: split the work into small map and reduce tasks and run them on thousands of cheap machines. This is the standard NoSQL-era case study of solving a business problem faster, cheaper and more effectively. <Cite id="big-data-intro-mapreduce" /> <Cite id="big-data-intro-nosql" />

**Business drivers** (the four named by McCreary and Kelly):

| Driver | In the Google MapReduce case |
|---|---|
| Volume | Billions of web pages, far more than one server can store or scan. |
| Velocity | Results (index, statistics) are needed again and again as the web changes. |
| Variability | Pages, logs and links have no fixed shape, so a fixed table does not fit. |
| Agility | Engineers must write new analyses quickly without learning parallel programming. |

**How it solved the problem**

1. Keep the data on many commodity machines (in GFS) and send the **code to the data**, not the data to the code.
2. The programmer writes only `map` and `reduce`; the library handles splitting, scheduling, shuffling and machine failures. <Cite id="hadoop-ecosystem-dean2004" />
3. To get more speed, add more cheap machines (scale out).

**Findings**

- **Faster:** thousands of machines work at the same time on one job.
- **Cheaper:** ordinary hardware replaces one costly big server, and a failed machine's task is simply re-run elsewhere.
- **More effective:** programmers without parallel-computing skills could write jobs; the paper reports almost 900 MapReduce programs at Google by September 2004 and 29,423 jobs run in August 2004. <Cite id="big-data-intro-mapreduce" />

**Conclusion:** MapReduce shows that scale-out, shared-nothing processing beats a single big server on time, cost and ease of use once data becomes huge. <Cite id="nosql-intro-gfg-intro" />
