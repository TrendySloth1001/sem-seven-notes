**In simple words:** HDFS is built to store a few very large files and read them from start to end quickly. It is a poor fit for millions of tiny files, because every file costs the NameNode memory and every read costs a seek. <Cite id="hdfs-apache-design" /> <Cite id="hdfs-gfg" />

**Why large datasets suit HDFS**

1. **Big blocks:** files are cut into large blocks (128 MB by default) and spread over many DataNodes, so one file can be bigger than any single disk.
2. **Streaming reads:** with big blocks, one seek is followed by a long sequential read, which gives high throughput. <Cite id="hdfs-apache-design" />
3. **Replication:** each block is copied (3 times by default), so a failed machine loses nothing.
4. **Computation moves to data:** MapReduce runs the task on the node that holds the block.

**Why small files hurt**

1. The NameNode keeps the metadata of every file, directory and block in RAM, about 150 bytes each. Ten million one-block files need about 3 GB of NameNode memory, so a billion files is infeasible. <Cite id="hdfs-cloudera-small" />
2. A 1 MB file still takes one block entry, so memory is wasted on metadata, not data.
3. Reading many small files means many seeks and hops between DataNodes, and MapReduce starts one map task per small file, so task start-up time dominates.

**Fix:** pack small files into a SequenceFile, HAR file or similar container. <Cite id="hdfs-cloudera-small" />

**Conclusion:** HDFS trades low-latency access to many small files for high throughput on few huge files.
