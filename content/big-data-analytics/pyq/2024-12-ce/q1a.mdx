**In simple words:** the **CAP theorem** (Eric Brewer) says that when a network failure splits a distributed database, it can keep only two of these three promises. <Cite id="nosql-intro-wiki-cap" /> <Cite id="nosql-intro-gfg-cap" />

- **Consistency (C):** every read returns the latest write, so all nodes show the same data.
- **Availability (A):** every request to a working node gets a reply.
- **Partition tolerance (P):** the system keeps running even when the network breaks the nodes into groups that cannot talk.

A cluster of many machines will face partitions, so P is a must. The real choice is **CP** (refuse some requests to stay correct, for example HBase) or **AP** (reply with possibly old data to stay up, for example Cassandra). Brewer himself says "pick two of three" is a simplification. <Cite id="nosql-intro-brewer-cap12" />

**ACID** is different. It is the promise of one database transaction: **A**tomicity, **C**onsistency, **I**solation, **D**urability. <Cite id="nosql-intro-wiki-acid" />

| Point | ACID | CAP |
|---|---|---|
| About | A transaction inside a database | A distributed system when the network fails |
| Properties | Atomicity, Consistency, Isolation, Durability | Consistency, Availability, Partition tolerance |
| Meaning of "consistency" | Data obeys its rules (valid state) | All nodes return the latest value |
| Goal | Correct transactions | Trade-off between correctness and uptime |
| Typical systems | RDBMS | Distributed NoSQL (many follow BASE) |

**Conclusion:** ACID guards the correctness of one transaction; CAP describes what a cluster must give up when the network breaks.
