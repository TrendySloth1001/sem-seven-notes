**In simple words:** **CAP theorem** (Eric Brewer) kehta hai ki jab network failure se distributed database ke nodes alag ho jaate hain, tab database in teen promises mein se sirf do hi rakh sakta hai. <Cite id="nosql-intro-wiki-cap" /> <Cite id="nosql-intro-gfg-cap" />

- **Consistency (C):** har read ko latest write milta hai, yaani saare nodes same data dikhate hain.
- **Availability (A):** jo node chal raha hai, uske paas aayi har request ko reply milta hai.
- **Partition tolerance (P):** network toot ke nodes ke groups alag ho jaayein, phir bhi system chalta rehta hai.

Bahut saari machines ke cluster mein partition hoga hi, isliye P zaroori hai. Asli choice hai **CP** (kuch requests reject karo taaki data sahi rahe, jaise HBase) ya **AP** (purana data de do taaki system up rahe, jaise Cassandra). Brewer khud kehte hain ki "pick two of three" ek simplification hai. <Cite id="nosql-intro-brewer-cap12" />

**ACID** alag cheez hai. Ye ek database transaction ka promise hai: **A**tomicity, **C**onsistency, **I**solation, **D**urability. <Cite id="nosql-intro-wiki-acid" />

| Point | ACID | CAP |
|---|---|---|
| About | Database ke andar ek transaction | Distributed system jab network fail ho |
| Properties | Atomicity, Consistency, Isolation, Durability | Consistency, Availability, Partition tolerance |
| "Consistency" ka matlab | Data apne rules follow kare (valid state) | Saare nodes latest value dein |
| Goal | Transactions sahi rahein | Correctness aur uptime ke beech trade-off |
| Typical systems | RDBMS | Distributed NoSQL (kaafi BASE follow karte hain) |

**Conclusion:** ACID ek transaction ki correctness bachata hai; CAP batata hai ki network toote to cluster ko kya chhodna padta hai.

Exam mein English mein likho: "CAP theorem states that a distributed store can guarantee only two of consistency, availability and partition tolerance at the same time."
