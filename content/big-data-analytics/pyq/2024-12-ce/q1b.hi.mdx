**In simple words:** ye statement **False** hai. Secondary NameNode backup ya standby NameNode nahi hai. Naam ke bawajood, NameNode mar jaaye to ye uski jagah nahi le sakta. <Cite id="hdfs-apache-guide" /> <Cite id="hdfs-gfg" />

**Justification.** NameNode file system ka metadata memory mein rakhta hai (**fsimage**) aur har change **edit log** mein likhta hai. Edit log bahut bada ho jaaye to NameNode ka restart bahut slow ho jaata hai. Secondary NameNode isse **checkpointing** karke theek karta hai, tay time par: <Cite id="hdfs-apache-guide" />

1. NameNode se fsimage aur edit log copy karta hai.
2. Dono ko merge karke nayi fsimage banata hai.
3. Use wapas bhej deta hai, taaki edit log chhota ho jaaye.

Ye clients ya DataNodes se baat nahi karta. Iski copy sirf pichle checkpoint tak ki hoti hai, isliye NameNode fail ho to recent changes kho jaate hain aur NameNode theek hone tak cluster band rehta hai. <Cite id="hdfs-wiki-hadoop" />

| Node | Kaam | Failure par takeover? |
|---|---|---|
| NameNode | Metadata rakhta hai, clients ko serve karta hai | Lagu nahi |
| Secondary NameNode | fsimage aur edit log merge karta hai | Nahi |
| Standby NameNode (HA) | Hot copy jo shared edit log padhti rehti hai | Haan |

Asli backup HDFS High Availability ka **Standby NameNode** hai. <Cite id="hdfs-apache-ha" />

**Conclusion:** Secondary NameNode ek checkpoint helper hai, backup nahi.

Exam mein English mein likho: "False. The Secondary NameNode only merges the fsimage and the edit log (checkpointing); it is not a backup of the NameNode."
