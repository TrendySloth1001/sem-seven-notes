**In simple words:** SQL databases store data in tables with a fixed structure and are queried with SQL. NoSQL ("not only SQL") databases store data as key-value pairs, documents, column families or graphs, with a flexible structure, and are built to scale out over many cheap servers. <Cite id="nosql-intro-gfg-sqlvs" /> <Cite id="nosql-intro-ibm-nosql" />

| Point | SQL (relational) | NoSQL |
|---|---|---|
| Data model | Tables of rows and columns | Key-value, document, column family or graph |
| Schema | Fixed in advance; changes are slow | Flexible or schema-less; each record can differ |
| Query language | SQL, common to all products | No common language; each product has its own API |
| Scaling | Mainly scale up (bigger server) | Scale out (more cheap servers) |
| Transactions | Full ACID | Often limited ACID; many use BASE (eventual consistency) |
| Joins | Strong support | Weak or none; related data is kept together |
| Best for | Structured data needing strict correctness (banking) | Huge, fast, varied data (social media, logs, catalogues) |
| Examples | MySQL, Oracle, PostgreSQL | MongoDB, Cassandra, Redis, Neo4j |

<Cite id="nosql-intro-aws-nosql" />

**Conclusion:** neither is always better. Many systems use both, called polyglot persistence: SQL for payments, NoSQL for the product catalogue and sessions. <Cite id="nosql-intro-fowler-poly" />
