**In simple words:** a relational database fixes the table columns before any data is stored and joins tables to answer questions. A NoSQL (document) database lets each record have its own fields and keeps related data together. <Cite id="nosql-intro-gfg-sqlvs" /> <Cite id="nosql-intro-ibm-nosql" />

**Comparison of schema design:**

1. **Fixed versus flexible schema.** In SQL the columns and types are defined first (schema on write). In NoSQL records can differ and the structure is applied when reading. **Example:** adding a column to a huge table is a slow migration; adding a field to a new document is instant.
2. **Normalised versus denormalised.** SQL splits data into many tables to avoid repeats. NoSQL stores related data in one record. **Example:** an order and its items are in one document.
3. **Joins versus embedding.** SQL combines tables with joins; NoSQL reads one document and needs no join, which is faster at scale but repeats some data. <Cite id="nosql-patterns-mongo-model" />
4. **Integrity.** SQL enforces types, keys and constraints in the database; in NoSQL the application must check them.
5. **Impact on business agility.** Flexible schema lets teams release features and add fields without downtime.
6. **Impact on development and data management.** Documents match objects in code, so there is less mapping; the cost is repeated data and more checking in code.

| Point | Relational | NoSQL (document) |
|---|---|---|
| Schema | Fixed, defined first | Flexible, per record |
| Structure | Tables, normalised | Documents, denormalised |
| Related data | Joins | Embedded in the record |
| Schema change | Slow migration | Easy |
| Integrity | Enforced by the database | Mostly by the application |
| Best for | Stable, structured data | Changing, varied data |

**Example:** an order in SQL needs three tables, Customer(Id, Name), Orders(OrderId, CustId, Date) and OrderItems(OrderId, Item, Qty), joined to read it. In a document store it is one record:

```json
{
  "orderId": 7,
  "customer": { "name": "Asha" },
  "date": "2026-08-17",
  "items": [
    { "item": "Pen", "qty": 2 },
    { "item": "Book", "qty": 1, "gift": true }
  ]
}
```

The second item has a `gift` field the first does not, which a fixed table could not allow without a new column. <Cite id="nosql-patterns-gfg-doc" /> <Cite id="big-data-intro-mongo" />

**Extend in the exam (add these to reach 10 marks):**

- **Advantages of flexible schema.** Fast changes, fewer NULLs, one read for related data.
- **Limitations.** Repeated data can go out of date, weak joins, and checks must be coded. <Cite id="nosql-intro-ibm-nosql" />
- **Applications.** Catalogues with varied attributes, user profiles and content suit documents; banking and billing suit tables.
- **Related point.** Neither is better everywhere; many firms use both (polyglot persistence). <Cite id="big-data-intro-nosql" />

**Conclusion:** a fixed schema gives order and integrity, a flexible schema gives speed of change, so the choice depends on how stable and how varied the data is.
